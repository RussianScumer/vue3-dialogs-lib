# Исправление: неограниченный рост `topZ` ломает бюджет z-index относительно Element Plus

Библиотека: `@korneevecin/vue3-dialogs-lib` (текущая версия 0.6.3).
Симптом в потребительском приложении (logistic): после нескольких дней использования
`ElMessageBox` / `ElNotification` (полоса z-index начинается с 2000 при каждой загрузке
страницы) отрисовываются **позади** окон приложения. Выглядит как «только в Safari»
лишь потому, что рост сохраняется per-browser в localStorage.

## Корневая причина

Z-index окна вычисляется как `zIndexBase + tier * topZ + z` (уровни: 0 фон,
1 сфокусированное, 2 превью примагничивания, 3 модальная подложка / окна с модальным
усилением, 4 контекстное меню).

`topZ` и per-window `z` — монотонные счётчики:

- **open**: новый дескриптор получает `z: ++topZ`
- **focus**: вся цепочка владельцев перенумеровывается `w.z = ++topZ` для каждого
  участника (пропускается, только если корень цепочки уже наверху и не свёрнут)
- **hydrate**: `topZ = max(сохранённый topZ, max сохранённых z, 10)`
- **persist**: `topZ` и значения `z` стека пишутся в хранилище как есть

Ничто их не уменьшает. Они переживают перезагрузки и растут без ограничения, поэтому
`zIndexBase + 3*topZ + z` рано или поздно пересекает любую фиксированную полосу оверлеев
(Element Plus: 2000). При `zIndexBase: 1000` коллизия начинается примерно с
`topZ ≈ 330` (модальный уровень) / `topZ ≈ 500` (сфокусированное окно, поскольку там
`z ≈ topZ`).

Якоря в минифицированном dist (имена в исходниках будут другими):

- фабрика состояния: `E({ stack: [], topZ: 10 })` — dist ~строка 493
- перенумерация фокуса: `function P(e){ for (let n of e) n.z = ++t.topZ }` — ~558
- страж фокуса: `root.z === t.topZ && !minimized` — ~563
- open: `z: ++t.topZ` в литерале дескриптора — ~779
- hydrate: `t.topZ = Math.max(o, 10)` — ~1022
- persist serialize: `topZ: e.s.topZ` — ~354
- потребители z-index: стиль окна ~1561, контекстное меню ~1634, модальная подложка
  ~1866, превью примагничивания ~1895

## Исправление: уплотнить счётчики до рангов

`z` используется только для **относительного порядка** (страж фокуса, сортировка
цикла alt-tab, сортировка усечения persist, max при hydrate) и как смещение внутри
уровня. Абсолютные значения не несут смысла. Поэтому заменяем «монотонный счётчик»
инвариантом:

> значения `z` — в точности `1..n` в порядке стека; `topZ === n` (n = длина стека,
> ограничена `maxWindows`).

### Реализация

1. Добавить один внутренний хелпер в модуль состояния, например `compact()`:
   - отсортировать `state.stack` по текущему `z` по возрастанию (стабильно; при
     равенстве сохраняется порядок массива),
   - переприсвоить `z = index + 1` на месте (мутировать те же объекты дескрипторов —
     они реактивны и повсюду используются по id; **не** заменять их),
   - установить `state.topZ = state.stack.length` (порог `max(…, 10)` оставлять,
     только если какой-то код на него опирается — ничего не должно; предпочесть
     просто `n` или `Math.max(n, 1)`).

2. Вызывать `compact()` после каждой мутации, меняющей порядок или состав:
   - в конце `open()` (после добавления дескриптора),
   - в конце перенумерации фокуса (`P`/`F`) — страж раннего выхода `root.z === topZ`
     продолжает работать без изменений, поскольку уплотнение сохраняет «корень
     наверху»,
   - в конце `hydrate()` — **игнорировать сохранённый аргумент `topZ` для целей
     порядка**: перенумеровать входящий стек и вывести `topZ` из него. Это лечит уже
     отравленный localStorage при первой загрузке после обновления, миграция не
     нужна. Сигнатуру `(stack, topZ)` сохранить для совместимости API.
   - при удалении/закрытии окна (поддерживает инвариант точным; не строго обязательно
     для корректности, поскольку значения только уменьшаются относительно границы).

   Стоимость O(n log n) при n ≤ maxWindows (8 в logistic) — пренебрежимо мала на
   каждый фокус. Порог не нужен; инвариант выполняется всегда, что проще тестировать
   и объяснять, чем «уплотнять, когда большое».

3. **Не** трогать четыре формулы z-index. При инварианте максимальный z-index любого
   элемента библиотеки — `zIndexBase + 4*n + 1` (уровень контекстного меню; окна
   модального уровня достигают `zIndexBase + 4*n`). Для logistic:
   `1000 + 4*8 + 1 = 1033` — навсегда ниже 2000 Element Plus.

4. Персистентность не требует изменения схемы: она уже пишет `topZ` + `z`, которые
   теперь малы по построению. Старые payload с огромными значениями уплотняются при
   hydrate.

### Документирование контракта потребителя

В README / документации опции `zIndexBase`: библиотека занимает
`[zIndexBase, zIndexBase + 4*maxWindows + 1]`; потребители должны держать свои полосы
оверлеев (Element Plus по умолчанию 2000+) выше неё. При стандартном `maxWindows` это
безопасно для любого `zIndexBase ≤ ~1960`.

## Тесты (vitest)

1. **Регрессия роста**: открывать/закрывать/переключать фокус окон далеко за старой
   точкой коллизии (например, 2000 чередований фокуса между владельцем и его
   потомком, плюс открытия). После каждого шага утверждать: `topZ === stack.length`,
   значения `z` — перестановка `1..n`, и каждый вычисленный z-index окна/подложки/меню
   ≤ `zIndexBase + 4*maxWindows + 1`.
2. **Сохранение порядка**: после уплотнения порядок фокуса, порядок цикла alt-tab и
   поведение «уже наверху → нет события focus» не меняются (сравнить последовательности
   до/после на малом стеке).
3. **Лечение отравленного хранилища**: hydrate с `topZ: 100000` и большими значениями
   `z` → состояние уплотнено, сохранённый payload перезаписан малым при следующем
   сохранении.
4. **Round-trip персистентности**: save → hydrate → порядок идентичен.
5. Существующий набор остаётся зелёным (фокус, цепочки владельцев, модальная
   блокировка, усечение до `maxWindows` — усечение сортирует по `z`, что продолжает
   работать).

## Релиз и проверка в logistic

1. Поднять версию библиотеки до **0.6.4**, опубликовать.
2. В logistic: `npm i @korneevecin/vue3-dialogs-lib@0.6.4` (package.json сейчас
   `^0.6.3`, поэтому свежая установка подхватит её; закоммитить изменение lockfile).
3. Воспроизведение до/после в Chrome (Safari не нужен):
   - засеять `localStorage['cr:windows']` огромным `topZ` (например, 2000) и
     соответствующими значениями `z` в стеке, перезагрузить;
   - на 0.6.3: открыть cargo → кликнуть неподтверждённый адрес → подтвердить →
     `ElMessageBox`/уведомление отрисовывается позади окон;
   - на 0.6.4: те же шаги, оверлеи сверху; проверить `cr:windows` — `topZ` теперь ≤ 8.
4. Sanity: стекирование окон, закрепление, модальное затемнение/inert,
   сворачивание/восстановление из таскбара, сохранённая раскладка после перезагрузки —
   всё без изменений.
5. Изменения кода приложения не нужны; комментарий в
   `frontend/src/plugins/windows/index.js` («below element-plus overlays (2000+)»)
   снова становится правдой.

## Отвергнутые альтернативы

- **Уплотнение только по порогу** (уплотнять при `topZ > N`): работает, но оставляет
  магическое число и окно, где инвариант ложен; всегда-уплотнение проще и дешевле.
- **Ранговый z-index в четырёх местах отрисовки**: тот же эффект, но трогает
  отрисовку вместо состояния и дублирует логику порядка в четырёх местах.
- **Поднятие начального z-index Element Plus в приложении**: лишь откладывает коллизию
  (счётчики растут без ограничения); неверный уровень для исправления.
- **CSS-переопределения z-index через `!important` для `.el-notification`/`.el-overlay`**:
  ломает взаимный порядок оверлеев; хрупко.
