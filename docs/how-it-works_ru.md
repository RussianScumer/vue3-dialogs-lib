# Как это устроено

Вся библиотека вытекает из одного решения:

> **Окно — это сериализуемый дескриптор в сторе, а не экземпляр компонента.**

Сворачивание, восстановление, персистентность, таскбар и «свёрнутое окно ничего не стоит» —
следствия этого решения, а не отдельные фичи.

## Дескриптор

Каждое окно — это один простой объект в одном массиве:

```ts
interface WindowDescriptor {
  id: string                       // crypto.randomUUID()
  name: string                     // ключ в карте компонентов, а НЕ компонент
  props: Record<string, unknown>   // только идентификаторы и примитивы
  state: unknown | null            // черновик состояния, которым владеет компонент содержимого
  title: string
  minimized: boolean
  x: number; y: number; w: number; h: number
  z: number
  meta: Record<string, unknown>    // учётные данные потребителя (версия сущности, ETag, …)

  closable: boolean                // возможности: сериализуемы, поэтому сохраняются вместе с окном
  minimizable: boolean
  draggable: boolean
  resizable: boolean
  minW: number; minH: number
  maxW: number | null; maxH: number | null   // null означает «без ограничения»
}
```

В нём нет ни ссылки на компонент, ни загруженной сущности, ни функции. Именно это и делает
`JSON.stringify` — а значит, и выживание после перезагрузки — вообще возможным. `name` — это
строковый ключ, который `WindowHost` ищет в карте компонентов во время рендера.

## Составные части

| Файл | Задача |
|---|---|
| `state.ts` | Реактивный стор: стек, `open`/`close`/`minimize`/`restore`/`focus`, дедупликация, вытеснение, ограничение геометрии. Никакого DOM, кроме реестра заголовков, нужного для передачи фокуса. |
| `createWindows.ts` | Фабрика плагина. Разрешает опции, создаёт один стор на приложение, предоставляет и то и другое, подключает персистентность. |
| `options.ts` | Умолчания, опции асинхронной загрузки по типам, разобранная раскладка клавиш и мемоизированный `resolve(name)`, превращающий функции-загрузчики в асинхронные компоненты. |
| `WindowHost.vue` | Рендерит по одному `BaseWindow` на каждый **несвёрнутый** дескриптор, удерживает уходящую рамку на время анимации и заново ограничивает геометрию при изменении размера вьюпорта. |
| `BaseWindow.vue` | Сам `<dialog>`: геометрия, заголовок, ручка перетаскивания, ESC, подъём и фокус по pointerdown, `data-vw-state`, контекст конкретного окна. |
| `WindowTaskbar.vue` | Renderless-компонент. Отдаёт множество свёрнутых окон в разметку потребителя, `registerFocusTarget` для подписки на фокус при сворачивании и `setTaskbarRect` для подписки на анимацию полёта к кнопке. |
| `useWindowDrag.ts` | Перетаскивание на pointer events плюс перемещение и изменение размера стрелками, а также зона примагничивания, взводимая перетаскиванием. |
| `useWindowResize.ts` | Восемь ручек изменения размера: математика указателя, ограничения размера и грани, двигающие `x`/`y`. |
| `useWindowFocus.ts` | Фокус внутрь окна при открытии и цепочка получателей фокуса — следующее окно, таскбар, открыватель — когда рамка размонтируется. |
| `useWindowState.ts` | Черновик состояния, хранимый в дескрипторе. |
| `useWindowContext.ts` | Поверхность управления конкретным окном через provide/inject. |
| `useViewport.ts` | Единственный на приложение трекер вьюпорта, создаваемый плагином. Один слушатель resize на сколько угодно окон. Безопасен для SSR. |
| `useKeymap.ts` | Единственный на приложение слушатель раскладки клавиш, создаваемый плагином. Висит на документе, действует на активное окно. Безопасен для SSR. |
| `persist.ts` | Снимок, проверка схемы, фильтрация при гидратации, отложенные записи, обнаружение записи из другой вкладки. |
| `geometry.ts` | Каскадное размещение, ограничение и математика зон примагничивания — чистые функции. |

## Жизненный цикл окна

```
win.open('itemEditor', { id: 42 }, { title: 'Item 42', w: 720, h: 520 })  → { id, result }
  │
  ├─ неизвестное имя?              → сразу throw (опечатки падают громко, а не молча)
  ├─ то же имя + те же props?      → восстановить и сфокусировать существующее окно, вернуть его id и result
  ├─ достигнут maxWindows?         → закрыть самое старое
  └─ push дескриптора { id, name, props, каскадная геометрия, z: ++topZ }
       │                            + записать неразрешённый result, до того как сработает событие `open`
       │
WindowHost рендерит `visible` (= стек минус свёрнутые)
       │
BaseWindow монтируется → dialog.show()  (немодально)
       │                  provideWindowContext(descriptor)
       │                  компонент содержимого монтируется и получает `v-bind="props"` + `windowId`
       │
minimize(id) → descriptor.minimized = true
       │        → выпадает из `visible` → содержимое РАЗМОНТИРУЕТСЯ немедленно, рамка переходит в `leaving`
       │        → дескриптор (и его черновик `state`) остаётся в стеке
       │
restore(id)  → minimized = false, z = ++topZ → содержимое монтируется снова, геометрия не меняется
       │
close(id)    → дескриптор удаляется из стека; от окна не остаётся ничего
       │        → его result разрешается как { ok: false, reason: 'closed' }, если ответа ещё не было
       │        → рамка переходит в `leaving` вместе с содержимым, пока не истечёт длительность анимации
```

`close()` безусловен и синхронен, поэтому `closeAll()` при выходе из системы невозможно
заблокировать. `requestClose()` — это защищённый путь: сначала собственный guard окна
(зарегистрированный смонтированным содержимым), затем общая для приложения опция `beforeClose`.
Только второй может увидеть **свёрнутое** окно, содержимое которого размонтировано, а значит,
guard'а уже не существует. Кнопка ✕ вызывает `requestClose`; вытеснение по `maxWindows` вызывает
`close`.

Оба guard'а ожидаются, поэтому окно остаётся в состоянии *closing* столько, сколько они занимают.
Это состояние — реактивное множество рядом с `docks`: живёт только в рантайме, поэтому дескриптор
и схема остаются на месте, а перезагрузка во время незаданного вопроса восстанавливает обычное
окно. Промис в полёте хранится рядом и выдаётся любому последующему `requestClose` с тем же id —
именно поэтому нетерпеливый второй клик не может спросить пользователя дважды. `close()` и
`closeAll()` очищают и то и другое, ни у кого не спрашивая: подвисший guard всё равно ответит — в
окно, которого уже нет, — и ничего не упадёт.

## Результаты окон

`open()` возвращает handle, а не id, потому что один только id не говорит, *ради чего* окно было
открыто. Ответ живёт в третьей рантайм-карте, рядом с guard'ами и по той же причине: она хранит
промисы, а значит, её нельзя было бы сохранить, даже если бы хотелось:

```
results: Map<id, { promise, settle }>   // только рантайм; никакого поля дескриптора, никаких изменений SCHEMA
```

```
open(...)              → deferResult(id); handle несёт промис
resolve(id, data)      → разрешить { ok: true, data }, затем close(id)
dismiss() / close(id)  → разрешить { ok: false, reason: 'closed' }
closeAll(), вытеснение,
  владелец закрывает
  дочернее окно        → то же самое для каждого затронутого окна
hydrate(stack)         → каждый восстановленный id получает уже разрешённое { ok: false, reason: 'restored' }
```

Два свойства несущие. **Результат никогда не зависает**: любой путь, удаляющий окно из стека,
проходит через `close()`, а `close()` разрешает промис. И **окно отвечает один раз**: разрешение
уже разрешённого промиса — это no-op, что и позволяет `resolve()` отдать значение и затем вызвать
`close()`, не рискуя, что закрытие его перезапишет.

Случай восстановления — единственное место, где модель дескрипторов и promise-API по-настоящему
расходятся. Открыватель гидратированного окна принадлежит предыдущей загрузке страницы, поэтому нет
ни промиса, который надо разрешить, ни вызывающего, ради которого это делать; стор разрешает его
как `restored` во время гидратации, вместо того чтобы оставить промис, на который никто никогда не
ответит. `resultOf(id)` читает промис любого окна обратно и отвечает `closed` для id, которого в
сторе больше нет.

Handle намеренно несовместим со строкой. Handle, который приводился бы к id, позволил бы вызову из
версии до 0.2 молча работать в проде и падать совершенно в другом месте; вместо этого он один раз
предупреждает в dev-режиме при приведении, а в остальном приводится к `[object Object]`.

И `minimize`, и `close` размонтируют рамку, а размонтированная рамка не может удержать фокус,
который она держала, — браузер роняет его на `<body>`. Поэтому `useWindowFocus` прямо перед
размонтированием запоминает, был ли фокус внутри этого окна, и если был, идёт по цепочке: окно,
оказавшееся сверху, — по заголовку, который оно зарегистрировало в сторе; затем таскбар, если
потребитель привязал `registerFocusTarget` и это было сворачивание, а не закрытие; затем элемент,
открывший окно. Реестром заголовков владеет стор, потому что первый шаг — это вопрос про `z` и
`minimized`, ответить на который может только стор: он переиспользует то же вычисляемое свойство
`activeId`, из которого рисуется `data-vw-active`, поэтому получатель фокуса не может разойтись с
визуально активным окном.

Каждый переход порождает событие (`open`, `close`, `focus`, `minimize`, `restore`, `geometry`,
`title`), на которое можно подписаться через `win.on(type, cb)`. Жест отчитывается перед стором,
когда он закончен: перетаскивание, изменение размера и стрелки пишут x/y/w/h прямо в дескриптор
кадр за кадром, а затем передают результат в `setGeometry`, поэтому `geometry` срабатывает один раз
на жест, а не на кадр, и сброс в зону примагничивания вызывает его однократно, из `snap()`.
Обратите внимание, чего это намеренно не видит: изменения черновика и промежуточного кадра жеста.
И то и другое пишется прямо в дескриптор, минуя методы стора, — именно поэтому персистентность
глубоко наблюдает за стеком, а не слушает события. `clampAll` при изменении размера вьюпорта молчит
по той же логике: этого перемещения никто не просил.

## Почему содержимое действительно исчезает на время сворачивания

`WindowHost` перебирает `visible`, то есть `stack.filter(w => !w.minimized)`. Свёрнутого окна в
списке нет, поэтому Vue размонтирует его поддерево: ни watcher'ов, ни таймеров, ни экземпляров карт
и гридов, никакого `KeepAlive`, никакого `v-show`. В playground это видно по живому счётчику
монтирований — сверните тикающий просмотрщик логов, и счётчик упадёт до нуля.

Цена в том, что содержимое не может держать свою форму в локальных `ref`. Ровно для этого и
существует `useWindowState`: черновик живёт в дескрипторе, который переживает монтирование.

## Анимация

Библиотека владеет конечным автоматом, потребитель владеет анимацией. `WindowHost` ставит на
`<dialog>` один атрибут и ничего больше:

```
data-vw-state="entering"   первый кадр после появления окна
                 "open"    со следующего кадра анимации и далее
              "leaving"    стор уже отпустил окно, рамка ещё нет
```

Истина остаётся за стором. `close()` и `minimize()` там синхронны — дескриптор исчезает или
становится свёрнутым в тот же момент, когда они возвращают управление, — а *хост* просто медленнее
отпускает рамку:

```
close(id)    → вне стека → рамка переходит в `leaving`, вместе с содержимым, и удерживается на время анимации
minimize(id) → вне `visible` → рамка переходит в `leaving`, содержимое размонтируется немедленно
restore(id)  → уходящая рамка возвращается к жизни, а не дублируется, и проигрывает анимацию в обратную сторону
```

Содержимое свёрнутого окна размонтируется в тот же миг, когда окно свернули. Задерживается именно
рамка, никогда не содержимое, — иначе главное обещание тихо превратилось бы в «размонтировано,
когда-нибудь». Закрывающееся окно сохраняет содержимое, пока гаснет, потому что окно, которое
сначала опустошает себя, читается как баг, а не как анимация.

Длительность читается из вычисленного значения `--vtd-motion-duration` **на элементе окна** —
именно поэтому для неё нет второго API: переопределение потребителем, media query и
`prefers-reduced-motion: reduce` (который базовая таблица стилей схлопывает в `0ms`) приходят через
одно и то же свойство, уже объявленное в таблице. Нечитаемо — таблица стилей не импортирована или
DOM'а нет вовсе — значит `0ms` и рамка, уходящая в том же тике, ровно как было до появления всего
этого.

Режим отказа, который стоит назвать вслух, — рамка, которая никогда не уходит: утечка, выглядящая
как работающая анимация и проходящая наивный тест. Ей мешают четыре вещи, и у каждой есть тест:
удержание ограничено 1000 мс, что бы ни говорила таблица стилей; `close()` уже уходящего окна
убирает его немедленно; размонтирование хоста убирает всё; и 50 циклов открытия-закрытия обязаны
не оставить ни одного элемента `<dialog>`. Уходящая рамка к тому же имеет `pointer-events: none` и
не реагирует на перетаскивание, изменение размера и стрелки, поскольку стор больше не знает id, о
котором его спросили бы.

Единственное, чего библиотека знать не может, — *куда* летит окно, потому что таскбар — это
разметка потребителя. Поэтому оно предлагается, а не предполагается:

```
setTaskbarRect(id, rect)   из слота WindowTaskbar, обычно из ref-колбэка кнопки
  ↓
taskbarRects: Map<id, Rect>              // только рантайм, рядом с `docks`
  ↓
--vtd-min-x / --vtd-min-y / --vtd-min-scale   на уходящей рамке
```

Смещения считаются от центра самого окна до центра кнопки и появляются только на рамке, которая
**сворачивается**: закрывающемуся окну лететь не к чему, поэтому то же базовое правило откатывается
для него к обычному затуханию. Таблица стилей анимирует отдельные свойства `translate` и `scale`, а
не `transform`, потому что `transform` — это позиция окна: индивидуальные свойства компонуются с
ней, а не перезаписывают её.

## Почему немодально

Окна открываются через `dialog.show()`, а не `showModal()` — включая модальные окна, см.
[Модальные окна](#модальные-окна).

- Одновременно может быть открыто несколько окон, страница за ними остаётся рабочей, а таскбар
  кликабельным — всё это невозможно с модальным диалогом, который делает инертным всё остальное.
- Телепортированные поповеры ваших собственных компонентов (меню select, датапикеры) нормально
  рендерятся поверх содержимого окна, потому что немодальный диалог находится в обычном контексте
  наложения.

Цена: нет браузерного top layer, поэтому `z-index` принадлежит библиотеке (`descriptor.z`,
поднимается на `pointerdown` и при `restore`), и браузер **не присылает запрос на закрытие**,
поэтому ESC обрабатывается слушателем `keydown`, а не событием `cancel` — диалог, открытый через
`.show()`, вообще никогда не получает `cancel`. Содержимое, которому ESC нужен для себя, сначала
вызывает `preventDefault()`; фоновое окно и нативный пикер тоже пропускаются.

## Геометрия

- Новые окна выкладываются каскадом: шаг 28px, перенос каждые 8 окон, размер по умолчанию 640×480.
- Перетаскивание пишет `x`/`y` прямо в дескриптор через Pointer Events с захватом указателя — один
  путь кода для мыши, тача и пера, и никаких слушателей на уровне `window`, которые могли бы
  протечь.
- Изменение размера работает так же, через восемь ручек, расположенных внутри границ окна. Оно
  заменило CSS `resize: both`, который давал только один угол, не мог соблюдать `minW`/`maxW` и
  вовсе не умел выражать изменение размера с запада или с севера — там при изменении ширины
  приходится двигать `x`/`y`, потому что на месте должна остаться *противоположная* грань. Любой
  путь, задающий размер, — указателем, клавиатурой или примагничиванием — проходит через
  `clampSize`, поэтому они не могут разойтись.
- `z` — это просто счётчик в дескрипторе; отрисованный `z-index` равен `zIndexBase + z`. Если
  держать базу вне сохранённого значения, сохранённый дескриптор остаётся валидным при смене базы.
  `focus()` пропускает запись, когда окно уже сверху, поэтому обычный клик внутри окна не будит
  watcher персистентности.
- `bounds.minVisible` (по умолчанию 80px) применяется при перетаскивании, при гидратации и при
  каждом изменении размера вьюпорта, поэтому окно не может оказаться недосягаемым.
- Ниже `mobileBreakpoint` отрисованная геометрия принудительно становится полноэкранной, а
  перетаскивание и изменение размера отключаются. Сохранённая геометрия не трогается, поэтому на
  широком вьюпорте окно возвращается на своё прежнее место.

## Примагничивание

Примагничивание назначает геометрию; оно не вводит вторую модель раскладки. Примагниченное окно —
всё тот же простой дескриптор с `x/y/w/h`, просто стор помнит — вне сохраняемого состояния, — какая
зона его туда поставила и как оно выглядело до этого:

```
docks: Map<id, { zone, prev }>     // только рантайм, поэтому дескриптор и SCHEMA не двигаются
```

```
перетаскивание идёт     → zoneFromPointer(pointer, viewport, snap) → store.preview → призрак в WindowHost
перетаскивание отпущено → snap(id, zone): один раз сохранить `prev`, назначить snapRect(zone), сфокусировать
перетаскивание сдвинуло
  примагниченное окно
  больше чем на 4px     → undockForDrag: вернуть размер до примагничивания, поместив окно под курсор.
                          По движению, а не по нажатию, чтобы клик не разворачивал окно обратно
двойной клик по
  заголовку             → snap(id, dockZone === 'max' ? 'none' : 'max')
закреплённое окно       → всё перечисленное отклоняется; см. «Закреплённые окна»
изменение размера
  за угол               → undock(id): сохранить новый размер, забыть зону
изменение размера
  вьюпорта              → clampAll: пристыкованные окна примагничиваются заново, плавающие — ограничиваются
```

Геометрия зоны берётся из `snapRect`, и призрак рисуется той же функцией, поэтому превью не может
разойтись с результатом сброса. Область примагничивания — это вьюпорт минус `snap.insets`, за счёт
чего фиксированный таскбар потребителя остаётся не перекрытым. Угол побеждает грань в
`zoneFromPointer`: угловая полоса широкая (по умолчанию 100px), а полоса грани — несколько
пикселей, иначе до четвертей было бы не добраться. Одна только нижняя грань не взводит ничего.

Поскольку `docks` живёт вне реактивного объекта `s`, отложенный watcher персистентности никогда не
видит наведения призрака, а перезагрузка возвращает примагниченное окно как обычное плавающее.

## Закреплённые окна

`fixed` — третий кусок рантайм-состояния конкретного окна, рядом с `docks` и `owners`, и у него
своя причина существовать именно там: закрепление переключается из заголовка, а значит, это не та
возможность, которую дескриптор мог бы нести без сдвига `SCHEMA`.

```
pins: Map<id, boolean>             // только рантайм, рядом с `docks` — никогда не сохраняется
```

**Наличие записи означает, что окно может быть закреплено; значение означает, закреплено ли оно
сейчас.** Окно, открытое без `fixed`, записи не имеет, кнопки закрепления не получает и рендерится
ровно так же, как до появления этой фичи, — что заодно оставляет число элементов управления
обычного окна на прежнем месте.

```
open(..., { fixed })   → pins.set(id, fixed); `fixed: false` — может быть закреплено, но не закреплено
setPinned(id, true)    → undock(id): явное закрепление старше примагничивания, геометрия сохраняется
полоса отрисовки       → закреплено: zIndexBase + topZ + z    не закреплено: zIndexBase + z
snap(id, …)            → отклоняется, пока окно закреплено, так что раскладка клавиш не исключение
перетаскивание /
  размер / стрелки     → единый предикат `interactive` в BaseWindow становится false, пока окно закреплено
close / closeAll /
  hydrate              → запись удаляется там же, где удаляется запись `docks`
```

`z` всегда положителен, поэтому `topZ + z` ставит каждое закреплённое окно выше любого
незакреплённого, сохраняя при этом относительный порядок закреплённых. `focus()`, `activeId` и всё
сохраняемое не затрагиваются: стек по-прежнему один, а вторая полоса существует только во время
рендера. Призрак примагничивания сидит на `zIndexBase + 2 * topZ + 1`, выше обеих полос, поэтому
превью сброса видно при любом закреплении.

У того, что полосы существуют только при отрисовке, есть одно следствие, которое стоит проговорить:
**верхнее окно не обязательно активное.** `activeId` — это наибольший `z` среди несвёрнутых окон, а
закрепление `z` не трогает, поэтому закреплённое окно, нарисованное поверх рабочего стола, — не то,
к которому обращаются ESC, раскладка клавиш или `data-vw-active`, если только оно не было
сфокусировано последним. Выводить `activeId` из полосы отрисовки означало бы, что закреплённое окно
невозможно оставить на заднем плане, а это противоположно смыслу закрепления: мини-плеер остаётся
на виду именно тогда, когда вы работаете в чём-то другом.

Цена явная и принятая: перезагрузка возвращает закреплённое окно незакреплённым и перетаскиваемым —
ровно так же, как возвращает примагниченное окно отстыкованным.

## Модальные окна

`modal` — четвёртый кусок рантайм-состояния конкретного окна, рядом с `docks`, `owners` и `pins`, и
у него самая резкая причина: модальное окно — это вопрос, поэтому оно не просто не сохраняется, как
закрепление, — оно целиком выбрасывается из блоба, ровно как окно с владельцем.

```
modals: Set<id>                    // только рантайм, рядом с `pins` — никогда не сохраняется
```

Именно Set, а не Map, в отличие от `pins`: модальность решается в `open()` и никогда не
переключается из заголовка, поэтому состояния «может, но выключено» для значения просто нет.

```
open(..., { modal })   → modals.add(id); minimizable принудительно false, как и у дочернего окна владельца
полоса отрисовки       → модальное: zIndexBase + 3 * topZ + z    (закреплённое: 1 * topZ, обычное: 0)
затемнение             → один элемент, на отрисованном z верхнего модального окна минус единица
все остальные окна     → `blocked` в BaseWindow становится true; `inert` на собственном <dialog>
ESC на модальном окне  → requestClose(id) — отклонить через guard'ы, а не свернуть
close / closeAll /
  hydrate              → запись удаляется там же, где удаляется запись `pins`
persistence            → отфильтровывается из блоба, рядом с окнами, у которых есть владелец
```

Полоса запрашивается как *«не заблокировано, пока открыто модальное окно»*, а не как *«является
модальным»*, и этот единственный предикат отвечает сразу на два вопроса: лист, которым владеет
модальное окно, поднимается в верхнюю полосу вместе с ним — вопрос, нарисованный под окном, которое
его задаёт, вопросом не является, — а *нижнее* модальное окно, заблокированное как и всё
остальное, остаётся под затемнением, где стопке диалогов и место.

Проход с `inert` — не новая механика. `BaseWindow` записывал и восстанавливал `inert` с тех пор,
как появились окна с владельцем, поэтому расширение одного условия покрывает и модальное окно,
открытое над окном, которое уже инертно как владелец: оно останется инертным и после исчезновения
модального.

| | Лист, привязанный к владельцу (`owner`) | Модальное окно уровня рабочего стола (`modal`) |
| --- | --- | --- |
| Что становится инертным | собственный `<dialog>` владельца | все остальные окна плюс `modal.inertRoot`, если задан |
| Подложка | нет | одно затемнение, под верхним модальным окном |
| Полоса | полоса владельца, на `owner.z + 1` | третья полоса, выше закреплённых и выше призрака |
| Другие окна | полностью интерактивны, включая перетаскивание | инертны |
| Персистентность | отфильтровано из блоба | отфильтровано из блоба |

**Дыра, названная вслух.** `inert` покрывает окна; он не покрывает страницу потребителя, а
затемнение останавливает только указатель. Поэтому Tab уходит из модального окна на страницу
позади, если только `modal: { inertRoot }` не назовёт элемент, который надо сделать инертным
заодно, — по подписке, потому что цикл focus trap — это основополагающая не-цель. Этот элемент не
может содержать `WindowHost`: `inert` покрывает поддерево, поэтому предок окон утащил бы модальное
окно вместе с собой — это проверяется по отрисованным рамкам и отклоняется с предупреждением в
dev-режиме, а не только описывается в документации.

Само затемнение несёт свою позицию, размер и наложение инлайново — по той же причине, по которой
инлайнова геометрия окна: модальное окно обязано блокировать клик даже без импортированной таблицы
стилей. `style.css` добавляет оттенок (`--vtd-scrim-bg`) и затухание, и больше ничего. `WindowHost`
держит затемнение, пока рамка модального окна ещё уходит, чтобы они гасли вместе, а не так, что
страница резко возвращается неприглушённой.

## Пресеты и размещение

`presets` — это карта именованных `WindowDefaults` в опциях, а `open(name, props, { preset })`
выбирает один из них. Он встаёт на шаг шире того приоритета, который уже существовал:

```
вызов open()  →  именованный пресет  →  спецификация компонента  →  умолчание библиотеки
```

Пресет назван в месте вызова — именно поэтому он старше собственной спецификации компонента и
уступает явным опциям того же вызова. Неизвестное имя бросает исключение в `open()`, до того как
что-либо будет вытеснено или открыто, ровно как неизвестный id владельца.

`placement: 'center'` центрирует окно вместо каскада. Центрированию нужен вьюпорт, которого у
`createStore(options)` нет — стор создаётся до `createViewport()`, — поэтому плагин передаёт его
через `store.attachViewport(view)` внутри собственной effect scope, а до тех пор стор держит то же
умолчание `1024 × 768`, с которого стартует `createViewport()`. Явные `x` или `y` по-прежнему
побеждают, по одной оси за раз.

## Подписи элементов управления

Стандартные элементы управления — это глифы, а строк библиотека не поставляет, поэтому их доступные
имена принадлежат потребителю. Это пятый кусок рантайм-состояния конкретного окна, рядом с `docks`,
`pins` и `owners`, и у него своя причина: подпись принадлежит локали работающего приложения, а не
окну. Сохранённая подпись восстановила бы прошлогодний перевод в страницу, которая с тех пор
переустановлена с новым.

```
controlLabels: Map<id, ControlLabels>   // только рантайм, рядом с `pins` — никогда не сохраняется
```

```
createWindows({ labels })  → имена уровня приложения, в ResolvedOptions
open(..., { labels })      → { ...spec.labels, ...opts.labels }, сохраняется только если непусто
labelsFor(id)              → { ...options.labels, ...controlLabels.get(id) }
рендер                     → :aria-label на –, ✕ и ▲; undefined не рендерит атрибут вовсе
кнопка закрепления         → :aria-pressed="pinned", поэтому одно имя покрывает оба направления
dev-предупреждение         → один раз на разрешённый объект опций, из onMounted в BaseWindow
close / closeAll /
  hydrate                  → запись удаляется там же, где удаляется запись `pins`
```

Предупреждение ключуется по разрешённому объекту опций в `WeakSet` уровня модуля — поэтому оно
живёт в обычном блоке `<script>` в `BaseWindow.vue`: всё, что внутри `<script setup>`, выполняется
на каждый экземпляр компонента, так что объявленное там множество было бы отдельным на каждую рамку
и не дедуплицировало бы ничего.

## Дочерние окна с владельцем

Окно может владеть другим окном. `open(name, props, { owner: id })` записывает связь в рантайм-карту
и перестраивает стек всей группы — именно это ставит дочернее окно ровно на `owner.z + 1`:

```
owners: Map<childId, ownerId>      // только рантайм, рядом с `docks` — никогда не сохраняется
```

```
open(..., { owner })   → owners.set(child, owner); поднять группу (владелец, затем его дети)
focus(любого)          → вся группа поднимается в порядке цепочки, относительное наложение сохраняется
у владельца есть
  ребёнок              → BaseWindow ставит `inert` на собственный <dialog> владельца, и только на него
minimize(владельца)    → отклоняется с dev-предупреждением: размонтирование бросило бы вопрос без ответа
requestClose(владельца)→ отклоняется: вопрос — это ребёнок, сначала ответьте на него
close(владельца)       → сначала закрываются дети, затем владелец
ESC на ребёнке         → requestClose(child) — отклонить, а не свернуть; его result разрешается как `closed`
persistence            → окна с владельцем отфильтровываются из блоба и выбрасываются при чтении
```

`inert` ставится императивно, а не биндингом, потому что то, что было там раньше, запоминается и
возвращается: владелец, который сам является чьим-то ребёнком, не должен потерять инертность из-за
того, что его собственный ребёнок исчез. Он пишется watcher'ом с `sync`, а не с дефолтным `pre`:
закрытие ребёнка возвращает фокус на заголовок владельца по цепочке получателей, а настоящий UA
отказывается фокусировать что-либо внутри инертного поддерева, поэтому атрибут должен исчезнуть к
этому моменту, а не на следующем тике.

Цепочка ограничена тремя звеньями, а неизвестный id владельца бросает исключение в `open()` ровно
так же, как неизвестное имя окна.

## Элемент `<dialog>`

Таблица стилей UA даёт `<dialog>` `position: absolute; margin: auto; inset: 0`; все три
переопределяются инлайново (`position: fixed`, `margin: 0`, `inset: auto`), иначе центрирование
дерётся с трансформацией. Позиционирование инлайново намеренно: библиотека работает вообще без
импортированной таблицы стилей, а `style.css` — только косметика.

## Персистентность

```
установка → read(storage[key])
            ├─ отсутствует / не парсится / не та `schema`    → игнорировать, начать с пустого
            ├─ дескриптор, чей `name` не зарегистрирован     → выбросить
            └─ выжившие: ограничить текущим вьюпортом, гидратировать, пометить как restored
watch(stack, deep) → debounce 300ms → storage[key] = { schema, topZ, stack, writer }
pagehide → отложенная запись сбрасывается синхронно (ничего, если запись уже остановлена)
событие storage по ключу → writer !== наш → перестать писать, onExternalChange(info)
                                             └─ info.resume() → перечитать, гидратировать, снова писать
```

При несовпадении схемы снимок по возможности *мигрируется*: каждое поле возможностей, которого
дескриптору не хватает, заполняется из умолчаний этого компонента, — и выбрасывается только тогда,
когда схема слишком стара, чтобы её прочитать. Выбрасывать читаемый блоб означало бы терять при
обновлении все открытые окна и все черновики, чего обещание пережить перезагрузку позволить себе не
может. Тот же путь починки исправляет и отредактированный вручную дескриптор, поэтому при
добавлении поля расширять нужно один путь кода.

Страница может исчезнуть внутри окна debounce, что уронило бы черновик, набранный за одно нажатие
до перезагрузки. Слушатель `pagehide` сбрасывает отложенную запись синхронно, поэтому последняя
правка переживает и перезагрузку, и закрытие вкладки, и заморозку в bfcache, и выгрузку вкладки на
мобильном; вкладка, уже переставшая писать после чужого изменения, молчит и во время этого сброса.

Всё, что трогает DOM, защищено проверкой `typeof window === 'undefined'`, поэтому импорт точки
входа в Node или во время SSR не делает ничего. `storage` — это любой объект
`{ getItem, setItem, removeItem }`, поэтому `sessionStorage`, обёртка над IndexedDB или адаптер с
серверным хранением подставляются без проблем.

`isRestored` не хранится в дескрипторе — стор держит множество гидратированных id в памяти, поэтому
`useWindowContext().isRestored` сообщает компоненту содержимого, пришло ли это монтирование из
хранилища или из свежего `open()`.

Поднимайте `SCHEMA` в `persist.ts` всякий раз, когда меняется форма дескриптора; устаревший блоб,
гидратирующийся в новый код, — самый вероятный источник трудновоспроизводимых багов в этой схеме.

### Безопасность между вкладками

`writer` — токен, выпускаемый один раз на вызов `setupPersist` и записываемый в **конверт** блоба, а
не в дескриптор: форма дескриптора не меняется, поэтому `SCHEMA` из-за него не двигается, старый
блоб без токена читается нормально, а старый код просто игнорирует ключ. Он отвечает ровно на один
вопрос: последняя запись этой вкладки породила значение, которое только что пришло?

Событие `storage`, чьё значение не принадлежит этой вкладке, — чужая запись. Всё нечитаемое тоже
считается чужим, включая очищенный ключ (`e.key === null`) и блоб, записанный версией без токена:
ничего из этого не пришло отсюда, а весь вопрос именно в этом. Принимающая вкладка ставит флаг
`stopped`, снимает отложенный debounce, чтобы запись, запланированная *до* чужой, не приземлилась
*после* неё, и отчитывается через `onExternalChange`. Бросившее исключение потребительское
поведение перехватывается — оно не должно уронить слушатель.

Флаг никогда не снимается сам. Возобновление по фокусу или по следующей мутации — это ровно тот
способ, которым одна сессия съедает другую, поэтому снимает его только `info.resume()`, и он
сначала гидратируется из хранилища.

События `storage` порождает только `localStorage`; любой другой адаптер просто никогда не доходит
до этого пути — без предупреждений и без детектирования возможностей. Слушатель добавляется в
`effectScope` плагина и удаляется вместе с ней, рядом с трекером вьюпорта и раскладкой клавиш.

## Подключение и SSR

Трекер вьюпорта, слушатель раскладки клавиш, watcher персистентности и его слушатель `storage`
создаются внутри отдельной `effectScope`, которую плагин останавливает из `app.onUnmount`, поэтому
ни один из них не переживает приложение, которому принадлежит.

`createWindows()` создаёт один стор на приложение и предоставляет его по symbol-ключу; `useWindows()`
— это `inject` с откатом на последнее установленное приложение, поэтому он работает и вне `setup()`
(навигационные guard'ы, сервисы, обработчики событий в обычных модулях). Внутри компонентов
внедрённый стор всегда побеждает, поэтому несколько экземпляров приложения остаются корректными.

Этот откат — привязка уровня модуля, а это ровно предел того, на что способен API без внедрения, и
на сервере он общий для всех рендерящихся запросов. `useWindows()`, вызванный там вне `setup()`,
ответит тем приложением, которое установилось последним, а это не обязательно то, которое сейчас
рендерится. В браузере это безопасно, потому что на документ приходится одно приложение; в
SSR-коде внедряйте стор внутри компонента через `inject` или передавайте его явно.

## Фокус

Немодальность означает **отсутствие focus trap**, и это намеренно. Но «нет ловушки» — это не то же
самое решение, что «нет фокуса вообще», с чего всё и началось: открытие окна теперь переводит фокус
на его первый достижимый по Tab элемент (с откатом на заголовок, у которого `tabindex="0"`), а
закрытие возвращает фокус тому, у кого он был в момент открытия окна.

Две ловушки порядка, каждая из которых стоила отладочной сессии и теперь закреплена тестами:

- `dialog.show()` выполняет *шаги фокусировки диалога* по спецификации UA, которые фокусируют первый
  фокусируемый элемент во всём диалоге — заголовок, поскольку он идёт перед содержимым. Поэтому хук
  фокуса должен регистрироваться **после** хука `show()`, иначе браузер молча его перезапишет. В
  jsdom `show()` этого не делает, поэтому ни один jsdom-тест это не поймает; нашлось в настоящем
  браузере.
- Асинхронный компонент — рекомендуемый способ регистрации окна — ещё не отрендерен в момент
  монтирования окна, так что фокусировать пока нечего. Фокус берёт заголовок, а `MutationObserver`
  передаёт его первому достижимому по Tab элементу, когда содержимое приезжает, — если только
  пользователь тем временем не переместил фокус сам.

Открыватель — это DOM-узел, поэтому он не может жить в дескрипторе. `BaseWindow` захватывает
`document.activeElement` в собственном setup — до того, как сможет украсть фокус, — и это полностью
избавляет стор от ссылок на DOM. Окно, восстановленное из хранилища при загрузке страницы, фокус не
забирает: у него нет открывателя, а красть фокус при загрузке — это проблема доступности, а не
фича.

## Локализация отказов

Окна — соседи в одном `v-for` внутри `WindowHost`. Если ничего не делать, ошибка, брошенная
содержимым одного окна, всплывает через этот `v-for`, пока хост патчится, и уносит с собой весь
рабочий стол: все остальные окна размонтируются из-за того, что одно оказалось сломанным. Для
оконного менеджера это неверный размен в любом случае, поэтому `BaseWindow` регистрирует
`onErrorCaptured`, рендерит `errorComponent` этого типа в собственном теле вместо содержимого и
возвращает `false`, чтобы остановить ошибку прямо здесь.

Цена остановки в том, что `app.config.errorHandler` её не увидит; вместо этого ошибка передаётся в
компонент ошибки пропсом — оттуда потребитель о ней и сообщает. Тот же компонент рендерит
`defineAsyncComponent`, когда падает сам чанк, так что «код не приехал» и «код приехал и упал»
выглядят для пользователя одинаково — разница всё равно не та, с которой он может что-то сделать.

## Чего библиотека намеренно не делает

Ни `showModal()`, ни браузерного top layer, никакого цикла focus trap, никаких хелперов
confirm/alert, никакой загрузки данных, никакого разрешения устаревания, никакой синхронизации между
устройствами, никакого тайлингового оконного менеджмента (пристыкованные рейлы, стопки вкладок,
сплиттеры), никакой дизайн-системы. [Модальные окна](#модальные-окна) — это узкое прочтение первых
двух пунктов: подписная затемняющая подложка и проход с `inert`, по окну, а не top layer.
Примагничивание к граням — единственное исключение, и оно остаётся чистой геометрией. Сворачивание и
восстановление не объявляются скринридерам, потому что для объявления нужны строки, а библиотека их
не поставляет. Паттерны, закрывающие пробелы, смотрите в [рецептах](./recipes.md).
