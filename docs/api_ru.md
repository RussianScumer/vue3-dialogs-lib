## Опции

Всё, что принимает `createWindows()`. Обязателен только `components`.

```js
import { createWindows } from '@korneevec/vue3-dialogs-lib'
import '@korneevec/vue3-dialogs-lib/style.css' // необязательная базовая таблица стилей

app.use(createWindows({
  components: {                          // имя -> компонент (рекомендуется async-загрузчик)
    itemEditor: () => import('./windows/ItemEditor.vue'),
    logViewer: () => import('./windows/LogViewer.vue'),
  },
  persist: { key: 'app:windows', storage: localStorage }, // уберите, чтобы отключить
  maxWindows: 8,
  bounds: { minVisible: 80 },            // сколько px окна всегда остаётся досягаемым
  snap: {                                // примагничивание к краям в духе Windows; уберите — будут значения по умолчанию
    enabled: true,
    edge: 12,                            // px от края, с которых взводится половина или максимизация
    corner: 100,                         // px от двух краёв, с которых взводится четверть
    insets: { bottom: 36 },              // держать примагниченные окна подальше от вашего таскбара
  },
  mobileBreakpoint: 768,                 // ниже — полный экран, без перетаскивания и ресайза
  zIndexBase: 0,                         // прибавляется к z каждого окна, чтобы перекрыть ваши оверлеи
  beforeClose: (d) => confirm(`Закрыть ${d.title}?`), // спрашивается в requestClose(), см. ниже
  keymap: {                              // Meta+стрелки для примагничивания, Alt+` для переключения; включено по умолчанию
    enabled: true,                       // false снимает все привязки, API стора не трогает
    bindings: { snapLeft: 'Ctrl+Alt+ArrowLeft' }, // на действие: аккорд, несколько или null
  },
  labels: {                              // доступные имена для стандартных кнопок –, ✕ и ▲
    minimize: 'Свернуть', close: 'Закрыть', pin: 'Поверх всех', // значений по умолчанию нет; см. «Подписи элементов управления»
  },
  presets: {                             // именованные наборы настроек окна, выбираются в каждом open()
    dialog: { modal: true, placement: 'center', w: 420, h: 200, draggable: false, resizable: false },
  },
  modal: { inertRoot: '#page' },         // необязательно: что становится inert, пока открыто модальное окно

  async: {                               // запасные состояния загрузки/ошибки для всех типов окон
    loadingComponent: WindowLoading,     // переопределения на тип живут в spec компонента
    errorComponent: WindowError,         // используется и когда содержимое окна бросает исключение
  },
}))
```

Голая функция в `components` считается async-загрузчиком. Простой функциональный компонент нужно
обернуть в `defineComponent`, чтобы он нёс опции компонента. `loadingComponent`, `errorComponent`,
`delay` и `timeout` можно задать и на тип в `WindowSpec`; окно, чьё содержимое бросило исключение,
рендерит тот же `errorComponent` внутри собственной рамки и не трогает остальные окна.

Смонтируйте хост один раз, над выводом роутера:

```vue
<router-view />
<WindowHost />
<WindowTaskbar v-slot="{ all, active, restore, focus, close, registerFocusTarget }">
  <div :ref="registerFocusTarget" class="my-taskbar" tabindex="-1">
    <button
      v-for="w in all"
      :key="w.id"
      :class="{ active: w.id === active }"
      @click="w.minimized ? restore(w.id) : focus(w.id)"
    >
      {{ w.title }}
      <span @click.stop="close(w.id)">✕</span>
    </button>
  </div>
</WindowTaskbar>
```

`WindowTaskbar` не рисует собственной разметки — внешний вид целиком принадлежит потребителю. Слот
получает `all` (все окна), `windows` (только свёрнутые), `active` (id верхнего окна или `null`),
`closing(id)` и `restore` / `focus` / `minimize` / `close` / `requestClose`. `registerFocusTarget`
необязателен: привяжите его как template ref — и таскбар станет тем местом, куда уходит фокус,
когда свёрнуто последнее окно, вместо элемента, который это окно открыл.

## Управление

Работает откуда угодно, в том числе вне `setup()`:

```js
import { useWindows } from '@korneevec/vue3-dialogs-lib'

const win = useWindows()
const { id, result } = win.open('itemEditor', { id: 42 }, { title: 'Item 42', w: 720, h: 520 })
win.minimize(id)
win.restore(id)
win.focus(id)
win.close(id)            // безусловно
await win.requestClose(id) // прогоняет guard-ы; resolve в false, если один из них отказал
win.closeAll()

win.updateProps(id, { id: 43 })
win.setMeta(id, { version: 7 })

await result             // чем окно завершилось — см. «Результаты окон»
win.resultOf(id)         // тот же промис, для окна, которое открывали не вы

win.activeId.value       // id верхнего несвёрнутого окна или null
const off = win.on('close', (e) => console.log(e.id)) // 'open' | 'close' | 'focus' | 'minimize' |
                                                     // 'restore' | 'geometry' | 'title' | '*'
```

`geometry` срабатывает один раз на перетаскивание, ресайз или сдвиг стрелками — в конце жеста, а не
на каждый кадр, — а также на `snap()` и `setGeometry()`. Сброс в зону примагничивания сообщается
один раз, из самого примагничивания.

Повторное ограничение всего стека после изменения размера вьюпорта проходит молча.

Вне `setup()` инжектить не из чего, поэтому `useWindows()` откатывается к стору последнего
установленного приложения. На сервере этот откат общий для всех запросов: в SSR-коде берите стор из
`inject` внутри компонента или передавайте его явно, а не тянитесь за ним.

`open()` дедуплицирует: то же `name` плюс поверхностно равные `props` восстанавливают и поднимают
уже существующее окно вместо открытия второго. Передайте `{ dedupe: false }`, если вам
действительно нужны два. Сверх `maxWindows` самое старое окно закрывается — молча и без опроса
guard-ов.

## Возможности окна

Каждое окно несёт собственные флаги и пределы размера. Они часть дескриптора, поэтому сохраняются
вместе с ним:

```js
win.open('itemEditor', { id: 42 }, {
  closable: false,      // прячет ✕; win.close(id) по-прежнему работает
  minimizable: false,   // прячет – и делает ESC бездействующим
  draggable: false,
  resizable: false,     // без ручек
  minW: 320, minH: 200,
  maxW: 900, maxH: null, // null означает «без предела»
})
```

Две опции в этой форме **не** лежат на дескрипторе и не сохраняются — `fixed`, которая закрепляет
окно поверх всех остальных, и `labels`, доступные имена его стандартных кнопок. Обе живут в
runtime-картах; см. [Закреплённые окна](#закреплённые-окна) и
[Подписи элементов управления](#подписи-элементов-управления).

Повторять всё это в каждом вызове — верный путь к ошибкам, поэтому компонент может нести собственные
значения по умолчанию. Дайте карте компонентов объект `{ component, ... }` вместо голого компонента:

```js
components: {
  itemEditor: { component: () => import('./windows/ItemEditor.vue'), w: 720, h: 520, minW: 320 },
  logViewer: () => import('./windows/LogViewer.vue'),
}
```

Приоритет: опции `open()`, затем значения компонента, затем библиотечные.

## Закрытие и guard-ы

`close(id)` безусловен и синхронен — `closeAll()` при выходе из аккаунта никогда не должен быть
блокируемым. `requestClose(id)` — путь с проверками, и именно его вызывает кнопка ✕:

```js
// на всё приложение, в опциях createWindows — покрывает и свёрнутые окна
beforeClose: (d) => !d.state?.dirty || confirm('Отбросить черновик?')
```

```js
// на окно, из его компонента содержимого
const { onBeforeClose } = useWindowContext()
onBeforeClose(() => !form.dirty || confirm('Отбросить черновик?'))
```

Любой guard может быть асинхронным — ради этого guard-ы и существуют: показать подтверждение,
дождаться ответа:

```js
onBeforeClose(async () => {
  if (!form.dirty) return true
  return await askTheUser() // ваше собственное окно, тост, что угодно, что резолвится
})
```

Пока guard решает, окно *закрывается*: `win.isClosing(id)`, computed `closing` из
`useWindowContext()` и слот-проп `closing(id)` у `WindowTaskbar`. Стандартные кнопки ✕ и – на это
время отключают себя. Второй `requestClose` в этот промежуток присоединяется к первому — тот же
промис, guard прогнан один раз, пользователя спросили один раз, — а guard, бросивший исключение,
считается отказом и предупреждает в dev. Ничто из этого не трогает дескриптор: перезагрузите
страницу посреди вопроса — окно вернётся обычным.

Пройти должны оба. **Guard окна существует только пока смонтировано содержимое** — прямое
следствие того, что «свёрнуто значит размонтировано»: свёрнутое окно, закрытое из таскбара,
покрывается только общим `beforeClose`. Всё, что должно держаться и для свёрнутого окна, кладите
туда.

## Результаты окон

`open()` возвращает `{ id, result }`. `result` — промис того, чем окно завершилось:

```ts
type WindowResult<T> =
  | { ok: true; data: T }
  | { ok: false; reason: 'closed' | 'restored' }
```

Окно завершает его из собственного содержимого:

```vue
<script setup>
const { resolve, dismiss } = useWindowContext()

function save(item) {
  resolve(item)   // завершает { ok: true, data: item }, затем закрывает окно
}
function cancel() {
  dismiss()       // завершает { ok: false, reason: 'closed' }, затем закрывает
}
</script>
```

```js
const saved = await win.open('itemEditor', { id: 42 }).result
if (saved.ok) refreshTheList(saved.data)
```

**Промис результата никогда не зависает.** Каждый путь, убирающий окно без ответа, завершает его как
`closed`: ✕, `close()`, `closeAll()`, вытеснение по `maxWindows` и закрытие дочернего окна
владельцем. `resolve()` отвечает первым, и закрытие, которое он выполняет, не может перезаписать это
значение. Guard, отказавший `requestClose`, оставляет окно открытым, а результат — ожидающим:
вопрос всё ещё на экране.

Дедуплицированный `open()` — то же имя, поверхностно равные props — присоединяется к уже открытому
окну, а с ним и к его ответу: одно окно на сущность значит один ответ, услышанный обоими вызовами.

### У восстановленного окна нет живого создателя

Это единственное место, где модель дескрипторов и promise-API по-настоящему расходятся, и
библиотека этого не скрывает. Окно, вернувшееся из хранилища, было открыто вызовом из прошлой
загрузки страницы — часто из прошлого дня. Отвечать некому, поэтому его результат завершён раньше,
чем кто-либо успеет его дождаться:

```js
await win.resultOf(restoredId) // { ok: false, reason: 'restored' }
```

`resultOf(id)` — ещё и способ добраться до результата окна, которое открывали не вы; id, которого
в сторе больше нет, отвечает `closed`. Ничто из результата не сохраняется: он живёт в runtime-карте
рядом с guard-ами закрытия, а дескриптор и `SCHEMA` не тронуты.

Чтобы типизировать `data`, дайте spec окна маркер `result`. Он существует только в типах — ключ
вырезается раньше, чем может попасть в дескриптор, — и деградирует до `unknown`, а не до ошибки:

```ts
export const components = {
  itemEditor: {
    component: () => import('./windows/ItemEditor.vue'),
    result: null as unknown as SavedItem,
  },
}

const saved = await useWindows<typeof components>().open('itemEditor', { id: 42 }).result
saved.ok && saved.data.name // SavedItem
```

## Внутри содержимого окна

```vue
<script setup>
import { useWindowState, useWindowContext } from '@korneevec/vue3-dialogs-lib'

const props = defineProps({ id: Number, windowId: String })

// черновик, переживающий сворачивание (размонтирование) и перезагрузку страницы
const form = useWindowState(props.windowId, () => ({ name: '', note: '' }))

const { setTitle, close, requestClose, onBeforeClose, minimize, isRestored, closing, resolve, dismiss } =
  useWindowContext()
setTitle(`Item ${props.id}`)
onBeforeClose(() => !form.name || confirm('Отбросить черновик?'))
</script>
```

`WindowHost` передаёт `windowId` каждому компоненту содержимого вместе с `props` дескриптора.

## Типизированный `open()`

Передайте карту компонентов аргументом типа — и `open()` проверит и имя окна, и props компонента
этого окна, в том числе сквозь async-загрузчик. Только типы; в рантайме ничего не меняется.

```ts
// windows.ts
export const components = {
  itemEditor: () => import('./windows/ItemEditor.vue'), // defineProps<{ id: number }>()
  logViewer: () => import('./windows/LogViewer.vue'),
}
export const useAppWindows = () => useWindows<typeof components>()
```

```ts
const win = useAppWindows()
win.open('itemEditor', { id: 42 })  // ок
win.open('itemEditor', { id: 'x' }) // ошибка: id должен быть числом
win.open('nope', {})                // ошибка: неизвестное окно
```

Та же карта типизирует и результат, если spec его объявляет — см.
[Результаты окон](#результаты-окон).

Зафиксируйте её один раз, как выше, и импортируйте алиас — голому `useWindows()` не с чем сверяться.
`windowId` подставляет хост, а не вызывающий. Окно, чьи props нельзя вывести (компонент — простой
объект, загрузчик с непрозрачным типом модуля), откатывается к `Record<string, unknown>`, а не
становится ошибкой типов.

## Контракт для потребителей

**Props окна — только id и примитивы** — никаких загруженных объектов, никаких значений из роута.
Окно переживает представление, которое его открыло, поэтому его содержимое само загружает свои
данные. Всё в дескрипторе сериализуется как есть; что-то не JSON-сериализуемое ломает
персистентность.

### Устаревание разрешаете вы

Сохранённый черновик может быть старше серверной копии. Библиотека ничего не загружает, поэтому
разрешить это не может. Что она даёт:

- `descriptor.meta` — сериализуемый слот для версии сущности или ETag;
- `isRestored` из `useWindowContext()` — `true`, если это монтирование пришло из сохранённого
  дескриптора, а не из свежего `open()`.

Паттерн: положите версию в `meta`, когда черновик начат, перезапросите при восстановленном
монтировании, сравните и дайте пользователю выбрать между черновиком и серверной копией. Молчаливая
перезапись параллельных правок — самый острый угол, который создаёт эта модель.

## Заметки о поведении

- Окна **немодальные** (`dialog.show()`): несколько сразу, фон остаётся рабочим, таскбар кликабелен,
  а телепортированные попперы ваших компонентов продолжают работать. Цена — нет top layer, поэтому
  `z-index` библиотека ведёт сама; сдвиньте его через `zIndexBase`, если у приложения есть
  собственные контексты наложения, которые нужно перекрыть.
- **ESC сворачивает** активное окно, а не закрывает его. Немодальный `<dialog>` не получает от
  браузера запроса на закрытие — `cancel` и ESC-для-закрытия принадлежат `showModal()`, — поэтому
  это работает на обработчике `keydown` на элементе окна. Он ничего не делает, когда: содержимое
  первым вызвало `preventDefault()`, окно не активно (Tab может добраться до фонового окна, не
  поднимая его), клавиша была нацелена на нативный пикер (`<select>`, `<input type="date">` и
  компания забирают ESC себе, не помечая событие обработанным) или окно `minimizable: false`.
- Открытие окна переносит фокус внутрь — на первый tabbable-элемент или на заголовок. Сворачивание
  или закрытие передаёт фокус дальше, в таком порядке: окну, оказавшемуся сверху, — в заголовок;
  таскбару, если он подписался через `registerFocusTarget` и это было сворачивание; элементу,
  открывшему окно. Никогда на `<body>` и вообще никогда, если фокус уже был уведён из этого окна.
  **Focus trap намеренно нет**: эти окна не модальные.
- Заголовок фокусируемый: стрелки двигают окно, shift+стрелки меняют его размер.
- Окна меняют размер за любую из восьми ручек с учётом `minW`/`minH`/`maxW`/`maxH`. Западная или
  северная ручка двигает ещё и `x`/`y`, чтобы противоположный край стоял на месте.
- `[data-vw-nodrag]` на любом элементе внутри заголовка не даёт ему начать перетаскивание.
- Окна заново ограничиваются при изменении размера вьюпорта, поэтому сжатие окна браузера не может
  оставить окно за экраном.
- Ниже `mobileBreakpoint` геометрия принудительно полноэкранная, перетаскивание и ресайз отключены;
  сохранённая геометрия не трогается и возвращается на широком вьюпорте.

## Персистентность

Персистентность пишет снимок с debounce (~300 мс). `storage` — любой
`{ getItem, setItem, removeItem }`, так что IndexedDB или серверный адаптер встают на место.

При загрузке дескриптор, чьё `name` больше не зарегистрировано, отбрасывается, а дескриптор с
недостающими полями — старая схема или blob, правленный вручную, — чинится из значений по умолчанию
этого компонента, а не выбрасывается. Снимок со схемой, слишком старой для чтения, отбрасывается
целиком.

### Две вкладки на одном ключе

Каждый blob несёт токен вкладки, которая его записала. Когда событие `storage` приносит значение,
которое эта вкладка не писала — другая вкладка на том же ключе или что угодно ещё, пишущее туда, —
принимающая вкладка **прекращает сохранять** и остаётся в этом состоянии. Это поведение по умолчанию
и не требует настройки: устаревшую вкладку можно восстановить, а вкладку, перезаписавшую чужую
сессию, — нет. Перезагрузить чужой снимок посреди редактирования было бы ещё хуже, поэтому
библиотека никогда не делает этого сама.

`onExternalChange` — место, где вы решаете, что с этим делать:

```ts
persist: {
  key: 'app:windows',
  storage: localStorage,
  onExternalChange(info) {
    // К моменту вызова запись уже остановлена. Проигнорируйте — и вкладка устареет,
    // спросите и перезагрузите, или примите снимок другой вкладки:
    info.resume() // перечитывает `info.key`, гидрирует стор, возобновляет сохранение
  },
},
```

Возвращение фокуса **не** возобновляет запись — возобновление и есть то, как теряются данные.
Только `resume()` или перезагрузка страницы. Учтите, что `resume()` гидрирует, то есть заменяет
окна этой вкладки окнами другой; несохранённые черновики в `useWindowState` уходят вместе с ними.

События `storage` испускает только `localStorage`. Другой адаптер — IndexedDB, серверный — молча
сохраняет сегодняшнее поведение «последний пишущий побеждает», без предупреждения и без обнаружения.
Используйте `sessionStorage` для окон на вкладку или ключ с id вкладки — и ничего из этого не
касается.

## Примагничивание

Потяните окно за заголовок к краю — и оно примагнитится, как в Windows: левый или правый край дают
половину, угол — четверть, верх максимизирует. Полупрозрачный призрак показывает цель до того, как
вы отпустите, а двойной клик по заголовку переключает максимизацию.

Оттаскивание примагниченного окна восстанавливает его прежний размер под курсором; ресайз за ручку
сохраняет новый размер и просто перестаёт считать окно примагниченным. Примагниченные окна следуют
за вьюпортом при изменении размера браузера, а плавающие лишь возвращаются в пределы досягаемости.

Примагничивание бездействует ниже `mobileBreakpoint`, где окна и так полноэкранные, и отключается
через `snap: { enabled: false }`. Область примагничивания — вьюпорт минус `snap.insets`, так что
фиксированный таскбар или шапка приложения никогда не перекрываются.

Управляйте им напрямую, когда нужно:

```js
win.snap(id, 'left', { w: innerWidth, h: innerHeight })  // 'left' | 'right' | 'max' | 'top-left' | …
win.snap(id, 'none', { w: innerWidth, h: innerHeight })  // обратно к геометрии до примагничивания
win.dockZone(id)                                          // текущая зона или null
```

Состояние примагничивания **живёт только в рантайме**: оно не часть дескриптора и не сохраняется.
После перезагрузки примагниченное окно возвращается обычным плавающим окном с той геометрией,
которую дало примагничивание.

## Закреплённые окна

`fixed: true` открывает окно поверх всех остальных, куда бы ни уходил фокус:

```js
win.open('miniPlayer', {}, { fixed: true })
```

Закреплённое окно нельзя перетащить, изменить в размере или примагнитить — ручек нет, заголовок не
тянется, стрелки его не двигают, двойной клик ничего не делает. Оно остаётся закрываемым и
сворачиваемым и появляется в таскбаре в свёрнутом виде, как любое другое окно.

В заголовке после ✕ есть кнопка-булавка (помечена `data-vw-pinned`, пока закреплено, чтобы её можно
было стилизовать); нажатие возвращает окно в обычную полосу — перетаскиваемым и примагничиваемым.
Повторное закрепление снова закрепляет его и сбрасывает любое примагничивание, которое оно успело
получить.

```js
win.isPinned(id)          // сейчас в закреплённой полосе
win.isPinnable(id)        // есть булавка для переключения — по ней рендерится кнопка в заголовке
win.setPinned(id, true)   // закрепить, сбросить примагничивание, сохранить геометрию
```

Само упоминание `fixed` делает окно закрепляемым, так что `fixed: false` даёт кнопку без
закрепления при старте, а окно, которое его вообще не упоминает, не тронуто — ни лишней кнопки, ни
второй полосы.

Состояние закрепления **живёт только в рантайме**, как и примагничивание: его нет на дескрипторе и
оно не сохраняется, так что после перезагрузки закреплённое окно возвращается незакреплённым и
перетаскиваемым. Это сделано намеренно — закрепление пользователь переключает в рантайме, а его
сохранение означало бы сдвиг схемы хранилища.

**Закреплённое ≠ активное.** Вторая полоса — вещь времени рендера: `activeId`, `data-vw-active`,
ESC и раскладка клавиш по-прежнему следуют за `z`, поэтому закреплённое окно, нарисованное поверх
рабочего стола, — не то окно, с которым говорит клавиатура, если оно не было ещё и последним
сфокусированным. Кликните по нему — и оно станет активным, как любое другое.

## Модальные окна

`modal: true` открывает окно поверх всех остальных полос, затемняет страницу за ним и делает все
остальные окна на рабочем столе `inert`, пока оно не закроется:

```js
const answer = await win.open('confirm', { message }, { modal: true }).result
```

Это по-прежнему `dialog.show()`, никогда не `showModal()`. Браузерного top layer нет, поэтому
`zIndexBase`, таскбар, закреплённая полоса и анимация ухода продолжают работать, а рабочий стол без
открытого модального окна байт в байт тот же, что и был.

- **Третья полоса рендера**, над закреплённой и над призраком примагничивания. Лист, открытый с
  `{ owner: <модальное окно> }`, поднимается вместе с ним; *второе* модальное окно поверх первого
  затемняется им и становится inert, как и положено стопке диалогов.
- **Один скрим**, под самым верхним модальным окном. Его позиция и наложение инлайновые, поэтому он
  блокирует указатель без подключённых стилей; оттенок — `--vtd-scrim-bg` в необязательной таблице
  стилей. Обработчика клика у него нет — закрытие по клику снаружи остаётся вашим решением.
- **Никогда не сворачивается**, принудительно, так же, как флаги дочернего окна: свёрнутое модальное
  окно заморозило бы рабочий стол, не оставив ничего, что могло бы ответить.
- **ESC закрывает его** через `requestClose(id)`, так что guard закрытия всё равно отрабатывает, а
  не сворачивает.
- **Никогда не сохраняется.** Модальное окно целиком вырезается из blob, ровно как дочернее окно:
  вопрос не должен возвращаться после перезагрузки. Решается в `open()` и никогда не переключается
  из заголовка, в отличие от булавки.

```js
win.isModal(id)            // открыто как модальное
win.topModalId()           // модальное окно, под которым лежит скрим, или null
win.isBlockedByModal(id)   // модальное окно открыто, и это окно — ни оно, ни его дочернее
```

**Tab не заперт.** Скрим останавливает указатель, а клавиатуру не останавливает ничто: без помощи
Tab изнутри модального окна уходит в вашу страницу. Focus-trap — не цель, поэтому ответ опциональный
и использует тот же механизм, что и всё остальное здесь:

```js
app.use(createWindows({ components, modal: { inertRoot: '#page' } }))
```

Этот элемент становится `inert` на всё время, пока открыто модальное окно, а тот `inert`, что у него
был, возвращается потом. Он **не должен** содержать `WindowHost` — `inert` покрывает поддерево, так
что предок окон утащил бы за собой и модальное окно; в разработке такой элемент предупреждает и
игнорируется.

### Пресеты

`presets` — именованные наборы тех же опций, что принимает `WindowSpec`, выбираемые в каждом вызове:

```js
app.use(createWindows({
  components,
  presets: {
    dialog: { modal: true, placement: 'center', w: 420, h: 200,
              draggable: false, resizable: false },
  },
}))

const ok = await win.open('confirm', { message }, { preset: 'dialog' }).result
```

Пресет называется в месте вызова, поэтому он перевешивает собственный spec компонента и проигрывает
явным опциям этого вызова: `open()` → пресет → spec → библиотечное значение по умолчанию.
Неизвестное имя пресета бросает исключение в `open()`, как и неизвестное имя компонента.

`placement: 'center'` ставит окно в середину вьюпорта вместо каскада; явные `x` или `y` всё равно
побеждают, по одной оси за раз. По умолчанию — `'cascade'`.

## Подписи элементов управления

Стандартные кнопки заголовка — глифы `–`, `✕` и `▲` булавки, — а библиотека не поставляет строк,
поэтому у них нет доступного имени, пока вы его не дадите:

```js
app.use(createWindows({
  components,
  labels: { minimize: 'Свернуть', close: 'Закрыть', pin: 'Поверх всех' },
}))
```

Они становятся `aria-label` на кнопках и больше ничем. Значений по умолчанию нет намеренно:
английское значение по умолчанию было бы неверным в каждом неанглийском приложении. В разработке
рабочий стол, рендерящий стандартную кнопку без имени, один раз предупреждает в консоли; production
молчит.

Окно может назвать свои кнопки само, слияние по ключам поверх общей опции — `open()` поверх spec
компонента поверх общих имён:

```js
win.open('settings', {}, { labels: { close: 'Закрыть настройки' } }) // оставляет общее «Свернуть»
win.labelsFor(id)                                                    // действующие имена
```

Булавка — переключатель: она несёт `aria-pressed` с состоянием закрепления, так что одно имя `pin`
покрывает оба направления. Как и `fixed`, подписи **живут только в рантайме** — они принадлежат
локали работающего приложения, а не окну, поэтому никогда не попадают в дескриптор или хранилище,
а общая опция просто читается заново при следующей загрузке.

Замена слота `controls` забирает всё целиком: ваши кнопки, ваши имена и никакого предупреждения.

## Клавиатура

Со сфокусированным заголовком стрелки двигают окно на 10px, а `Shift`+стрелки меняют его размер.
Из любого места внутри окна работает ещё и раскладка клавиш:

| Действие | Привычный аккорд | Аккорд, который доживает |
| --- | --- | --- |
| `snapLeft`, `snapRight`, `snapMax`, `snapNone` | `Meta`+`←` / `→` / `↑` / `↓` | `Ctrl`+`Shift`+ та же стрелка |
| четверти, по часовой от верхней левой | `Meta`+`Shift`+`↑` / `→` / `↓` / `←` | `Ctrl`+`Shift`+`1`…`4`, в порядке чтения |
| `focusNext`, `focusPrev` | `Alt`+`` ` `` / `Alt`+`Shift`+`` ` `` | `Ctrl`+`` ` `` / `Ctrl`+`Shift`+`` ` `` |

**Почему два аккорда.** Привычный обычно не доходит: Windows забирает `Win`+стрелку под Snap
Assist, GNOME и KDE забирают `Super`+стрелку под тайлинг, GNOME забирает `Alt`+`` ` `` под
переключение группы, а Chrome на macOS читает `Cmd`+`←` как «Назад». Оконный менеджер перехватывает
клавишу выше браузера, так что страница не может ни заметить это, ни предупредить, ни забрать
обратно — второй аккорд стоит в одном модификаторе от всего, что резервирует рабочий стол, и именно
на нём функция работает на практике. Четверти не могут переиспользовать там стрелки, поскольку
`Ctrl`+`Shift`+стрелка уже занята половиной, поэтому это цифры в порядке чтения — сопоставляются по
`event.code`, потому что `Shift`+`1` на одной раскладке даёт `!`, а на другой — что-то ещё.

**Аккорды действуют на активное окно** — верхнее несвёрнутое, несущее `data-vw-active`, — где бы
ни был фокус. Раскладка — один слушатель `keydown` на документе, созданный в effect scope плагина
рядом с трекером вьюпорта и снимаемый при размонтировании приложения; без DOM он бездействует, так
что SSR не затронут. Клик по окну поднимает *и* фокусирует его, поэтому окно сверху — то, с которым
говорит клавиатура.

Аккорды примагничивания идут через тот же `snap(id, zone, view)`, что и сброс мышью, поэтому
уважают `snap.enabled`, `snap.insets`, флаги `draggable`/`resizable` окна и бездействие ниже
`mobileBreakpoint`. Нажатие внутри `<input>`, `<textarea>` или `contenteditable` принадлежит
текстовому полю и никогда не доходит до окна — `Meta`+`←` на macOS это начало строки, а
`Ctrl`+`Shift`+стрелка везде выделение по словам. Слушатель стоит на фазе всплытия, так что
содержимое, вызвавшее `preventDefault()`, оставляет клавишу себе, а ваши собственные обработчики
могут опередить библиотеку.

Каждая привязка переназначается, и переопределение заменяет **оба** стандартных аккорда действия,
так что вы никогда не унаследуете коллизию, которой не просили:

```js
keymap: {
  bindings: {
    snapLeft: 'Ctrl+Alt+ArrowLeft',      // один аккорд заменяет стандартный
    snapMax: ['Ctrl+ArrowUp', 'F11'],    // или несколько
    snapNone: null,                      // или вообще ни одного
  },
}
```

Аккорд — модификаторы плюс клавиша, в любом порядке и регистре: `Meta`/`Cmd`/`Super`/`Win`,
`Ctrl`, `Alt`/`Option`, `Shift`. Клавиша сопоставляется и с `event.key`, и с `event.code`, так что
`Backquote` и `` ` `` называют одну физическую клавишу — важно там, где `Alt` превращает её в
мёртвую. Модификаторы должны совпадать точно, поэтому переназначение половины никогда не проглотит
четверть над ней.

Переключение поставляется независимо от раскладки:

```js
win.focusNext()   // следующее несвёрнутое окно по z, по кругу; фокусирует его заголовок, возвращает id
win.focusPrev()
```

Оба пропускают свёрнутые окна и любое окно, у которого сейчас есть дочернее, поскольку рамка
владельца `inert`, пока его вопрос на экране.

Призрак — элемент `.vw-ghost`, стилизуемый через `--vtd-ghost-bg`, `--vtd-ghost-outline` и
`--vtd-ghost-radius`.

## Стилизация

`style.css` — только косметика: раскладка и позиционирование инлайновые, так что окна работают и без
него. Перестраивайте внешний вид через кастомные свойства `--vtd-*`: `--vtd-font`,
`--vtd-font-size`, `--vtd-radius`, `--vtd-border`, `--vtd-shadow`, `--vtd-bg`, `--vtd-fg`,
`--vtd-accent`, `--vtd-head-bg`, `--vtd-head-fg`, `--vtd-head-pad`, `--vtd-body-pad`,
`--vtd-foot-pad`, `--vtd-btn-hover-bg`, `--vtd-ghost-bg`, `--vtd-ghost-outline`,
`--vtd-ghost-radius`, `--vtd-scrollbar-thumb`, `--vtd-scrollbar-track`, `--vtd-scrollbar-width`.

Таблица стилей читает эти свойства и никогда их не объявляет, поэтому задавайте их где удобно —
на `:root`, в классе темы, инлайн-стилем на `<html>` — и наследование донесёт их до окон; нет
никакого объявления `.vw`, которое пришлось бы перебивать специфичностью. Оставьте одно незаданным —
применится встроенное значение по умолчанию, включая значения для `prefers-color-scheme: dark`.
В playground случай 8 — живой редактор всех этих свойств.

### Готовые темы

Рядом с базовой таблицей стилей поставляются готовые палитры. Они объявляют цветовые токены и
ничего больше — ни радиусов, ни шрифтов, ни отступов, ни анимации, — поэтому сочетаются с любой
формой, которую вы уже задали.

```js
import '@korneevec/vue3-dialogs-lib/style.css'
import '@korneevec/vue3-dialogs-lib/themes/dracula.css'
```

```html
<html data-vtd-theme="dracula">
```

Атрибут и класс `vtd-theme-dracula` равнозначны, и любой из них работает на `<html>`, на обёртке или
на одном окне (у `BaseWindow` один корневой элемент, поэтому `class` проваливается насквозь). Для
переключателя тем в рантайме подключите один раз `themes/all.css` и меняйте атрибут:

```js
import '@korneevec/vue3-dialogs-lib/themes/all.css'

document.documentElement.dataset.vtdTheme = 'nord'
delete document.documentElement.dataset.vtdTheme // обратно к значениям библиотеки по умолчанию
```

Каждая палитра обёрнута в `:where()`, так что стоит на нулевой специфичности: ваши собственные
объявления `--vtd-*` всё равно побеждают, и можно взять палитру и переопределить два токена поверх.

Поставляются: `dracula`, `nord`, `solarized-light`, `solarized-dark`, `gruvbox-dark`,
`catppuccin-latte`, `catppuccin-frappe`, `catppuccin-macchiato`, `catppuccin-mocha`, `tokyo-night`,
`one-dark`, `one-light`, `monokai`, `monokai-pro`, `rose-pine`, `everforest-dark`,
`kanagawa-wave`, `github-light`, `github-dark`, `ayu-dark`, `material-darker`, `nightfox`.

Палитра красит окна и ничего больше. Даже `color-scheme` ограничен: каждая тема задаёт его как
`--vtd-color-scheme`, который `style.css` применяет на `.vw`, так что нативные элементы форм внутри
окна соответствуют палитре, а страница вокруг — её холст, её собственные скроллбары, её элементы
управления — остаётся ровно такой, какой её сделал ваш CSS, даже с атрибутом на `<html>`.

Скроллбар тела тоже следует за темой, и не только переключением светлое/тёмное: `style.css` задаёт
`scrollbar-color` на `.vw` из собственного цвета текста рамки, поэтому каждая палитра красит его,
ничего не объявляя. Переопределите через `--vtd-scrollbar-thumb` и `--vtd-scrollbar-track` или
перейдите на узкий скроллбар через `--vtd-scrollbar-width: thin`. Свойство наследуется, так что
ваш собственный скроллер внутри тела получит тот же оттенок.

Всё, что вы рисуете сами и что должно следовать за палитрой, может читать те же токены; таскбар в
playground делает это через `background: var(--vtd-head-bg, #26262b)`.

### Активное окно и ручки

Верхнее окно несёт `data-vw-active`, так что `.vw[data-vw-active]` — ваш селектор для стилизации;
`--vtd-border-active` и `--vtd-shadow-active` — сокращения, по умолчанию равные неактивным
значениям, чтобы базовый вид не менялся. Ручки ресайза — элементы `.vw__grip` с
`data-vw-grip="n" | "se" | …`; по умолчанию они прозрачны.

Библиотека не поставляет строк: подписи кнопок заголовка и их `aria-label` приходят из слота
`controls` у `WindowHost`/`BaseWindow`.

Окно — три ряда: заголовок, тело, подвал. Прокручивается только `.vw__body`, поэтому содержимое
выше рамки остаётся внутри него, а кнопки действий в необязательном слоте `footer` остаются
досягаемыми, пока пользователь уменьшает окно.

## Известные ограничения

- **Нет объявления при сворачивании/восстановлении.** Сворачивание убирает поддерево, ничего не
  сказав скринридеру. Исправление требует строк, а библиотека их по замыслу не поставляет;
  потребитель с настроенным i18n сделает это в несколько строк на `win.on('minimize')`.
- **У свёрнутого окна нет собственного guard-а** — см. [Закрытие и guard-ы](#закрытие-и-guard-ы).
- **Две вкладки на одном ключе персистентности не сливаются.** Второй пишущий обнаруживается, и
  принимающая вкладка прекращает запись вместо потери сессии — см.
  [Персистентность](#персистентность), — но ничего не сливается, а вкладка, игнорирующая
  `onExternalChange`, устаревает до перезагрузки.
- **Модальное окно не запирает Tab.** Скрим блокирует указатель; клавиатура по-прежнему достаёт до
  вашей страницы, пока вы не укажете на неё через `modal: { inertRoot }` — см.
  [Модальные окна](#модальные-окна).
- Ручки ресайза сидят во внешних 4px окна — там же, куда попадает и скроллбар тела.

## Чего библиотека не делает

`showModal()` и браузерный top layer, focus-trap, хелперы confirm/alert, загрузка данных и
разрешение устаревших черновиков, синхронизация раскладки между устройствами, тайловый оконный
менеджер (пристыкованные панели, стопки вкладок, сплиттеры) и встроенная дизайн-система.
Примагничивание ограничено описанными выше жестами к краям в духе Windows.
[Модальные окна](#модальные-окна) — узкое прочтение первых двух пунктов: опциональный скрим и
`inert`-обход, по одному окну, а top layer и focus-trap по-прежнему за бортом.
